---
title: Move to a new device
description: "Move the complete .znn directory with rsync, verify it, and explicitly hand off the producer."
---

R11 is implemented locally, pending release. Open **Install & upgrade → Migrate to a new device**, or use `nomctl migrate`. Run the workflow from the original server.

Migration copies the **entire configured node directory**, including wallet files, producer keys, `config.json`, hidden files, chain data, and other directories. It also copies the exact installed znnd executable and creates the replacement service. The original data remains intact.

## Requirements

- Both devices run systemd Linux with the same CPU architecture, rsync, and a migration-capable nomctl. Install nomctl on the replacement before beginning; do not deploy a node there.
- The original uses the standard root service generated by nomctl, with no service overrides. Custom service users or units require a separate migration plan.
- SSH must already authenticate without a prompt, using a previously verified host key. Use an SSH host alias or `user@hostname`. For a non-root SSH account, select `--sudo`; remote `sudo -n nomctl` must work. The SSH connection uses the credentials and known-hosts file available to the root account running nomctl.
- The replacement data directory, executable path, and service must be unused. Their parent directories must exist and use canonical paths. Existing nodes are never overwritten.
- Keep recovery backups outside the original data directory. Allow space for a protected chain/znnd restore point, a separate encrypted wallet/config backup, and the replacement copy. The destination reserves room for the largest file during resume and enforces the usual free-space and 75% disk-use limits. A receiver checks the reserve once per second; this is a sampled guard, not a filesystem quota.
- Use local/wildcard RPC and P2P bind addresses. The preview checks the replacement's configured ports locally; firewall and external reachability still need to be checked for the new server.

Relative links resolving inside the data directory are supported. Absolute links, external links, dangling links, sockets, pipes, and device files block migration. Bring external dependencies inside `.znn` first. An absolute producer-key path must become a relative wallet path. File modes, numeric owner/group IDs, modification times, hardlinks, and internal links are preserved and checked; the destination data root is restricted to mode `0700`. The first version does not migrate extended attributes or ACLs.

## Preview and copy

```bash
sudo nomctl migrate plan --to root@new-server \
  --destination-data /root/.znn \
  --destination-binary /usr/local/bin/znnd \
  --destination-service go-zenon
```

Optional connection flags: `--port 22`, `--remote-nomctl /usr/local/bin/nomctl`, and `--sudo`.

The preview saves the two host identities, exact paths, architecture, znnd version/commit and SHA-256, data size, and ports. Neither node is stopped. Downtime depends on disk speed and network throughput: the **whole transfer and content verification happen while stopped**. There is no live initial copy or fixed duration promise. `nomctl migrate cancel` discards only an untouched preview.

```bash
sudo nomctl migrate transfer
```

Confirm the copy and choose an encryption passphrase for the separate wallet/config backup. For unattended invocation, provide `NOMCTL_WALLET_PASSPHRASE` securely in the process environment and pass `--yes`. The passphrase is never sent to the replacement.

Before copying, nomctl creates and verifies the recovery files. It then stops and disables both node services and installs persistent start blocks. These blocks survive disconnection and reboot; ordinary nomctl mutations, including scheduled backups, are refused while a host is blocked.

Rsync shows transfer progress without listing wallet/config contents or filenames. It copies into a private staging directory and retains partial data for resume. Completed contents and required metadata are checked against the stopped source before promotion to the final path. Both nodes remain stopped after a successful copy.

## Explicit handoff

```bash
sudo nomctl migrate status
sudo nomctl migrate handoff
```

Handoff requires another confirmation (`--yes` for unattended use). Nomctl reconfirms the original's start block and stopped state, checks the replacement, then permits only the replacement to start. The post-change health check observes RPC, peers, advancing heights, restarts, and the intended installed/running znnd SHA-256. It also verifies the transferred producer key against configuration before startup.

The original stays blocked after success, including at boot. Its data and recovery files are retained. Removing old data is a separate operator task; no migration step deletes it. Set up backups and verification schedules, alerts, and any orchestrator on the replacement. External backup directories and those host-level settings are not copied.

## Interrupted or failed migration

```bash
sudo nomctl migrate status --json
sudo nomctl migrate resume
```

`resume` continues copying from saved state and does not start either node. A changed source, conflicting host identity, changed executable, or invalid link is refused. Stale files may be deleted **inside migration staging only** when repairing a copy. Neither the original nor the promoted destination is a deletion target.

If the connection fails during promotion, retry `resume`. If it fails during handoff, inspect status and retry `handoff` to reconcile the saved state and health. If health fails, the replacement may be running and the original remains blocked. A missing response is reported as unknown; it never triggers an automatic restart of the original.

To abandon a started migration:

```bash
sudo nomctl migrate return
```

After confirmation, nomctl first stops and persistently blocks the replacement, then restarts and checks the original using its retained data. If the replacement cannot be reached or confirmed stopped, the original is not restarted. Retry `return` after connectivity is restored. The replacement remains blocked after return, including at reboot. Returning does not copy newer chain data back to the original; it catches up normally.

Migration state lives in `/var/lib/nomctl/migration`. Do not remove its guard or use manual service changes to bypass a pending handoff. Completed/returned records are retained; this first version does not automatically reset them for another migration.
